The **Relativity Short Message Format** (**RSMF**) is a file format for short message data, such
as SMS, chat applications and enterprise messaging, defined by the eDiscovery software vendor
Relativity. An RSMF file packages one or more conversations, with their participants, events and
attachments, so that a document review platform can ingest them as structured records instead of
as a rendered document. RSMF files use the `.rsmf` extension.

RSMF is a conversion format. An RSMF file is produced by a tool from data that was collected or
exported elsewhere, such as a mobile device extraction or a chat platform export, and what it
contains depends on what that tool chose to write.

## Structure

An RSMF file is an [EML](eml.md) message: it is compliant with RFC 5322 (Internet Message Format)
and uses MIME. Relativity describes it as essentially a ZIP archive wrapped in an EML file.

The file consists of:

* a **header** with file-level metadata, in standard mail headers and in headers prefixed with
  `X-RSMF-`;
* a **body**, a `text/plain` part that contains the extracted text of the conversation;
* exactly one **attachment** named `rsmf.zip`, encoded as base64, with `Content-Disposition` set
  to attachment.

### Header

`X-RSMF-Version` is the only required header. Relativity documentation states that it should be
included in the first line of the header. Optional headers include `X-RSMF-Generator`,
`X-RSMF-BeginDate`, `X-RSMF-EndDate` and `X-RSMF-EventCount`. Version 2.0 adds optional headers
such as `X-RSMF-Application`, `X-RSMF-Custodian`, `X-RSMF-Participants`,
`X-RSMF-AttachmentCount` and `X-RSMF-EventCollectionID`. Custom headers are allowed if they use
the `X-RSMF-` prefix.

During processing, Relativity maps the `X-RSMF-` headers to fields, and the standard `To`, `From`
and `Subject` headers to the corresponding email fields.

### Body

The body is generated by the tool that created the file, not by the review platform. Relativity
uses it as the extracted text of the document: it is the text that is searched and shown in the
extracted text view.

### rsmf.zip

The archive contains a file named `rsmf_manifest.json` at its root, and every attachment and
avatar image that the manifest refers to. An attachment is referenced by its `id`, which must be
the exact file name inside `rsmf.zip`, including the extension.

## Manifest

The manifest is a JSON document with four required root properties:

* `version`
* `participants`, a list of the people taking part, each with an `id` and optionally a display
  name, an email address and an avatar
* `conversations`, a list of conversations, each with an `id`, a `platform` and a `type` of
  either `direct` (fixed participants) or `channel` (participants can change)
* `events`, a list of events, each linked to a participant and a conversation by `id`

In schema version 2.0.0 the event `type` is one of `message`, `disclaimer`, `join`, `leave`,
`history` or `unknown`. A message event can carry a body, reactions, attachments, edits, a
`deleted` flag and an `importance`. A `parent` property links a message to the thread it belongs
to.

Timestamps must be ISO 8601 date/time values.

Relativity publishes a JSON schema for the manifest and a validator library, see External Links.

## Versions

Two versions are in use, 1.0 and 2.0. Version 2.0 adds read receipts, the direction of a message
(`incoming` or `outgoing`, relative to the custodian), history events and custom platform icons.
Several properties that are required in 1.0, such as the participant, timestamp and conversation
of an event, are optional in 2.0.

## Forensic Considerations

* An RSMF file is a derived representation. It shows what its generator wrote into the manifest
  and the body, not the source data, and a review platform can only display what the manifest
  contains. Fidelity to the source should be verified against the original extraction or export.
* The body and the manifest are written independently by the generator. Search runs against the
  body, while per-event metadata, such as senders and timestamps, is held in the manifest and is
  not searchable as text in Relativity.
* The schema requires ISO 8601 timestamps but its examples carry no time zone offset. Reveal
  documents that it assumes RSMF dates to be in UTC. A timestamp without an offset is ambiguous
  and the time zone basis should be confirmed with the producer of the file.
* An attachment whose file name does not match its `id` in the manifest is not linked to its
  message. The Relativity validator reports both an attachment missing from the archive and a
  file in the archive that the manifest does not reference.
* Relativity deduplicates RSMF files with the email method, hashing the header, the recipients,
  the body and the attachments. The same conversation collected from two custodians will
  normally have different headers and is not flagged as a duplicate.
* Relativity recommends no more than 10,000 events per file and does not support RSMF files larger
  than 2 GB. Large conversations are therefore usually split ("sliced") into several files, for
  example by participants and by time period, and a single file may hold only part of a
  conversation.

## Opening an RSMF File

Because an RSMF file is an EML message, it can be opened in an email application after changing
the extension from `.rsmf` to `.eml`. This shows the headers, the extracted text and the
`rsmf.zip` attachment, which can be saved and opened as an ordinary ZIP archive to read the
manifest.
